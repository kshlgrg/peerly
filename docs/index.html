02 • early traction

Students Are Already Trying It

Students in the university have started using PeerLy, which means the idea escaped the localhost basement.

The first goal was not to become another heavy social network. The goal was a low-pressure campus interaction layer: enter, match, talk, leave, repeat. Early student use gives us real behavior to observe: awkward openers, fast skips, curiosity around video, and strong demand for lighter social spaces.

04 • feature stack

Core Features

Random MatchingMode-specific queues pair students into one-on-one rooms without profiles.
Realtime ChatWebSocket messages relay instantly while the chat history stays alive in the session.
Consent VideoText rooms can request video. Nobody gets camera-jumped without accepting.
Room GamesTic Tac Toe, Connect Four, Dice Race, and Loot Tiles keep silent rooms from becoming haunted.
Skip FlowOne tap exits the room, cleans partner state, and requeues users properly.
Savage InterfaceRetro terminal panels, CRT filters, and microcopy with a little attitude.

06 • architecture

How It Works

React UIRoutes for home, chat, and video; session state in Zustand.
WebSocketJoin, match, message, game, skip, request video.
FastAPIAsync matching queues, partner maps, room cleanup.
WebRTCOffer, answer, ICE signaling through backend.
P2P MediaCamera and mic stream browser-to-browser, not through the server.

07 • tech stack

Stack

Small enough to move fast, real enough to survive actual users.

React + ViteFast frontend iteration, component-based UI, production static build.
ZustandShared session state for chat history, mode changes, games, and WebRTC signaling.
FastAPIAsync Python backend for WebSocket control, matching, skip flow, and room state.
WebRTCDirect peer-to-peer video and audio after signaling completes.
RenderHosted static frontend plus backend web service for production deployment.
